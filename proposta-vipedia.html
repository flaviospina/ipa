Diagnóstico

O relatório é gerado, é salvo no Drive — e o link se perde no caminho

O envio acontece em dois passos. Primeiro o navegador manda as respostas e o Apps Script grava a linha na aba RESPOSTAS, junto com um identificador. Depois o navegador manda o relatório pronto, o Apps Script salva o PDF no Drive e procura aquela linha pelo identificador para escrever o link na coluna Relatório (link).

A busca nunca encontra a linha. O identificador é gravado passando por uma função de limpeza que troca hífens por espaço, mas a comparação é feita contra o identificador original, com os hífens.

backend/apps-script.gs — a origem
function clean(v) {
  return String(v || '').replace(/[=+\-@\t\r\n]/g, ' ').trim().slice(0, 200);
}                              └── o hífen entra aqui, junto com = + @

// na gravação (linha 294) o ID passa por clean()
.concat([..., linkRelatorio || '', clean(data.id || '')]);

// no arquivamento (linha 103) a comparação é com o ID cru
if (String(values[i][idCol]) === String(data.id)) { ... }
Verificação — executada agora, com a função real do sistema
ID gerado no navegador    : "ipa-msvtr73m-sozkl3"
ID gravado na planilha    : "ipa msvtr73m sozkl3"
Comparação do arquivamento: NUNCA encontra a linha

O hífen entrou nessa lista porque a função protege a planilha contra injeção de fórmula — no Excel e no Sheets, um texto que começa com =, +, - ou @ vira fórmula executável. A proteção está certa. O erro foi aplicá-la a um campo que também serve de chave de busca.

E há um agravante que explica por que isso passou despercebido por tanto tempo: quando a busca falha, o Apps Script ainda responde { ok: true, code: 'archived' }. A tela mostra “✓ relatório arquivado” e ninguém tem motivo para desconfiar. O PDF realmente está no Drive, na pasta IPA - Relatórios — só não há como ligá-lo à pessoa pela planilha.

Correção imediata, independente de todo o resto: tirar o hífen da lista de caracteres limpos no ID (a proteção anti-fórmula continua valendo para nome, organização e função), e fazer o arquivamento responder ok: false quando não encontrar a linha. São duas linhas. Proponho fazer isso hoje, antes de qualquer migração — assim os diagnósticos que rodarem nas próximas semanas já ficam completos.

Outras fragilidades

O que mais encontrei ao ler o sistema inteiro

CríticoUma chave só abre os dados de todas as empresas

O Painel do Consultor autentica com uma chave única guardada em PANEL_KEY. Quem tem a chave lista todas as respostas de todas as organizações. Não existe separação por empresa em lugar nenhum — nem no painel, nem na planilha, nem no Apps Script.

É exatamente o problema que você quer resolver, e é também uma exposição de LGPD: um cliente não pode ter acesso técnico aos dados comportamentais dos funcionários de outro.

AtençãoA chave viaja na barra de endereço

O painel autentica por GET ...?action=list&key=SUACHAVE. Chave em query string fica registrada no histórico do navegador, nos logs do servidor e no cabeçalho Referer de qualquer link clicado a partir dali. Login de verdade — POST e cookie de sessão — resolve.

AtençãoO 360° aceita qualquer nome digitado

Hoje o avaliador externo digita livremente o nome do avaliado e a organização. “Maria Silva”, “maria silva” e “Maria S.” viram três pessoas diferentes na base. Não há como saber quantos convites foram enviados, quantos responderam, nem impedir que a mesma pessoa responda cinco vezes.

Sem convite com identidade travada, o 360° não tem como produzir um número confiável — e é justamente o número que dá valor ao 360°.

AtençãoO estilo de cada palavra está implícito na posição

O cálculo deduz o estilo pela posição da palavra dentro da lista (i<3?'A':i<6?'C':...), em dois arquivos diferentes — no Apps Script e no engine.js. Reordenar uma palavra no questionário muda silenciosamente a pontuação de todo mundo, e as duas cópias podem divergir sem que nada acuse.

AtençãoChaves de API dentro de um script compartilhado

GEMINI_API_KEY e PANEL_KEY vivem nas propriedades do Apps Script. Qualquer pessoa com permissão de edição na planilha consegue lê-las. Na arquitetura nova elas ficam em arquivo de configuração fora da pasta pública do site.

Arquitetura

De onde para onde

Hoje: o navegador fala direto com um Apps Script, que grava numa planilha e num Drive. O controle de acesso é uma chave de texto. A separação entre empresas não existe — ela é feita a olho, filtrando uma coluna.

Proposta: o navegador fala com uma API no seu próprio servidor, que grava no MySQL. Cada requisição carrega a identidade de quem está logado, e toda consulta é filtrada por empresa_id no próprio banco. Um administrador de empresa não consegue ver dados de outra nem forçando a URL — não é uma regra de tela, é uma condição de consulta.

Premissa que preciso confirmar: o prefixo itthri79_ no nome do banco é padrão de cPanel — o mesmo formato do seu ambiente na HostGator. Estou assumindo PHP 8 + MySQL/MariaDB em hospedagem compartilhada, que é o que roda ali. Se a hospedagem for outra (VPS com Node, por exemplo), o banco continua igual e só muda a linguagem da API.

As três definições que carregam as decisões importantes

O restante é convencional. Estas três merecem leitura, porque é nelas que os problemas de hoje deixam de ser possíveis:

1 · Separação entre empresas, garantida por estrutura
CREATE TABLE usuarios (
  id           INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  empresa_id   INT UNSIGNED NULL,        -- NULL = administrador geral
  nome         VARCHAR(120)  NOT NULL,
  email        VARCHAR(160)  NOT NULL,
  senha_hash   VARCHAR(255)  NOT NULL,   -- password_hash(), bcrypt
  papel        ENUM('admin_geral','admin_empresa','consultor','gestor') NOT NULL,
  status       ENUM('ativo','inativo','bloqueado') NOT NULL DEFAULT 'ativo',
  trocar_senha TINYINT(1)    NOT NULL DEFAULT 1,  -- senha inicial é temporária
  ultimo_login_em   DATETIME NULL,
  tentativas_falhas SMALLINT UNSIGNED NOT NULL DEFAULT 0,
  bloqueado_ate     DATETIME NULL,
  criado_por   INT UNSIGNED  NULL,
  criado_em    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_usuarios_email (email),
  CONSTRAINT ck_escopo CHECK (
    (papel =  'admin_geral' AND empresa_id IS NULL) OR
    (papel <> 'admin_geral' AND empresa_id IS NOT NULL)
  ),
  CONSTRAINT fk_usuarios_empresa FOREIGN KEY (empresa_id)
    REFERENCES empresas(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

O CHECK torna impossível existir um administrador de empresa sem empresa — que seria, na prática, alguém enxergando tudo. A API monta cada consulta com WHERE empresa_id = :sessao_empresa, e para o administrador geral esse filtro é liberado explicitamente, nunca por omissão.

2 · A validação das respostas vira regra do banco
CREATE TABLE avaliacao_respostas (
  avaliacao_id BIGINT   UNSIGNED NOT NULL,
  palavra_id   SMALLINT UNSIGNED NOT NULL,
  quadro       TINYINT  UNSIGNED NOT NULL,   -- 1, 2 ou 3
  peso         TINYINT  UNSIGNED NOT NULL,   -- 0 a 11
  PRIMARY KEY (avaliacao_id, palavra_id),
  UNIQUE KEY uq_peso_por_quadro (avaliacao_id, quadro, peso),   -- ← a chave da coisa
  CONSTRAINT ck_peso  CHECK (peso   BETWEEN 0 AND 11),
  CONSTRAINT ck_quadro CHECK (quadro BETWEEN 1 AND 3),
  CONSTRAINT fk_resp_aval FOREIGN KEY (avaliacao_id)
    REFERENCES avaliacoes(id) ON DELETE CASCADE,
  CONSTRAINT fk_resp_palavra FOREIGN KEY (palavra_id)
    REFERENCES palavras(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

Hoje a regra “cada peso de 0 a 11 aparece uma única vez por quadro” existe só como código no Apps Script. Ali, uq_peso_por_quadro faz o próprio banco recusar a gravação. Nenhum caminho — API nova, importação de histórico, correção manual — consegue furar isso.

3 · O convite 360° com identidade travada
CREATE TABLE convites_360 (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  ciclo_id      BIGINT UNSIGNED NOT NULL,
  relacao       ENUM('gestor','par','liderado','cliente_interno','outro') NOT NULL,
  email         VARCHAR(160) NULL,        -- opcional: convite por link também serve
  token_hash    CHAR(64)     NOT NULL,    -- SHA-256; o token só existe no e-mail
  status        ENUM('pendente','enviado','respondido','expirado','cancelado')
                NOT NULL DEFAULT 'pendente',
  enviado_em    DATETIME NULL,
  respondido_em DATETIME NULL,
  expira_em     DATETIME NOT NULL,
  avaliacao_id  BIGINT UNSIGNED NULL,     -- preenchido ao responder
  UNIQUE KEY uq_convite_token (token_hash),
  UNIQUE KEY uq_convite_avaliacao (avaliacao_id),  -- uma resposta por convite
  CONSTRAINT fk_convite_ciclo FOREIGN KEY (ciclo_id)
    REFERENCES ciclos_360(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

O avaliador recebe um link e não digita nada além das respostas: quem está sendo avaliado e em que relação já vêm no convite. uq_convite_avaliacao garante uma resposta por convite. E a empresa passa a ver, em tempo real, quantos convites saíram e quantos voltaram.

O anonimato do respondente continua preservado: o relatório 360° só mostra médias por relação, e apenas quando o mínimo de respondentes daquele grupo for atingido — proponho três. O convite identifica o convite, não expõe o autor da resposta na tela de ninguém.

  • Administrador da empresa: entra com o próprio login e vê apenas a sua empresa — participantes, resultados, mapa de calor da equipe, relatórios individuais e exportação
